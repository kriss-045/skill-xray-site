## Structural Metrics (Measurable Tells)
### 1. Excessive Comment-to-Code Ratio
**Tell:** Comments constitute 30-35% of code. AI maintains systematic, repetitive documentation; humans write comments inconsistently (5-20% with high variance).
**Concrete example:**
```python
# Initialize the list
my_list = []
# Loop through numbers 1 to 10
for i in range(1, 11):
# Add the number to the list
my_list.append(i)
# Return the list
return my_list
```
**Fix:** Delete 50-70% of comments. Keep only comments explaining "why," not "what." If the code is self-explanatory (descriptive variable names, clear logic), remove the comment. Ratio target: 5-15%.
**Evidence:** EMPIRICAL (ANOVA analysis across C, C++, Java, Python shows highest statistical significance for model identification)
**Source:** https://arxiv.org/html/2502.17749v2
---
### 2. Perfect Indentation Uniformity
**Tell:** Nearly 100% adherence to consistent indentation (e.g., exactly 2 spaces per level throughout). Human code occasionally has 2 spaces, 4 spaces, or tabs due to copying from different files.
**Fix:** Introduce minor indentation inconsistencies. Edit sections from other files that may have different indentation. Allow natural variation. Aim for 90%+ consistency, not 100%.
**Evidence:** EMPIRICAL (measured as ratio of most-common indentation pattern)
**Source:** https://arxiv.org/html/2502.17749v2
---
### 3. Uniform Function Length
**Tell:** Functions remarkably consistent in length (average 15-20 lines, tight variance). Human code ranges 3-100+ lines depending on purpose.
**Fix:** Write some one-liner utility functions, some 5-line helpers, some 50-line complex logic. Let function length be driven by actual need, not by a formula.
**Evidence:** EMPIRICAL (measured as average lines per function)
**Source:** https://arxiv.org/html/2502.17749v2
---
### 4. Consistent Nesting Depth
**Tell:** Average nesting depth remains consistently shallow (max 3 levels across all functions). Human code uses varied nesting (1 level for simple logic, 5+ levels for error handling and complex conditions).
**Fix:** Some functions should have 1 nesting level, others 5+. Use nested conditions where they fit the problem, not for consistency.
**Evidence:** EMPIRICAL (measured as average nesting depth per function)
**Source:** https://arxiv.org/html/2502.17749v2
---
### 5. Consistent Function Name Length
**Tell:** Function names maintain consistent word length (average 2.3 words). Human code uses `get`, `getUserById`, `getUserIDFromDatabaseAndTransformToJSON` interchangeably (high variance).
**Fix:** Write some single-word function names (`process`, `run`, `filter`), some longer descriptive ones. Variance is natural.
**Evidence:** EMPIRICAL (measured as average function name length)
**Source:** https://arxiv.org/html/2502.17749v2
---
### 6. Consistent Variable Name Length
**Tell:** Variable names maintain consistent length (average 2.1 words): `userData`, `userId`, `userEmail`. Humans use `u`, `user`, `userInformation`, `x` interchangeably.
**Fix:** Use variable names of varying length based on scope and context. Loop counters can be `i` or `x`. Important module-level variables should be descriptive. Mix short and long.
**Evidence:** EMPIRICAL (measured as average variable name length)
**Source:** https://arxiv.org/html/2502.17749v2
---
### 7. Perfect Naming Convention Consistency
**Tell:** 95%+ adherence to one naming convention (camelCase or snake_case). AI maintains one pattern consistently when it occurs; humans switch between conventions naturally.
**Fix:** Introduce deliberate naming variation. Use both `userData` and `user_data` where appropriate. If the codebase has mixed conventions, use that naturally rather than forcing consistency.
**Evidence:** EMPIRICAL (10 quantitative metrics including 4 naming-consistency metrics)
**Source:** https://arxiv.org/html/2502.17749v2

## Stylistic Patterns (Opinion-Based but Consistent)
### 8. Over-Commenting (Redundant Explanations)
**Tell:** Tutorial-style comments explaining basic syntax and self-evident logic.
**Concrete example:**
```python
# Check if x is greater than 5
if x > 5:
# Print the message
print("x is large")
```
**Fix:** Delete comments on straightforward logic. Add comments only where the "why" is non-obvious. For complex algorithms or counterintuitive logic, explain the reasoning, not the mechanics.
**Evidence:** OPINION (practitioner observation from code review)
**Source:** https://medium.com/according-to-context/llms-have-revived-these-5-anti-patterns-in-software-engineering-e685159fc4d8
---
### 9. Excessive Print/Debug Statements
**Tell:** Debugging print or log statements left in code without removal, cluttering production output.
**Concrete example:**
```python
def process_data(data):
print("Starting process_data")
result = transform(data)
print(f"Result is: {result}")
return result
```
**Fix:** Remove all debug print statements. If logging is needed, use a proper logging framework (Python: logging module, JavaScript: winston, etc.) at appropriate levels, not console.log or print.
**Evidence:** OPINION (practitioner observation)
**Source:** https://medium.com/according-to-context/llms-have-revived-these-5-anti-patterns-in-software-engineering-e685159fc4d8
---
### 10. Single-Use Helper Functions
**Tell:** Functions created and called only once, adding unnecessary abstraction layers.
**Concrete example:**
```python
def format_user_name(name):
return name.upper()
user = format_user_name("alice") # Called once
```
**Fix:** Inline one-off helpers. Replace with `user = "alice".upper()`. Create a function only if it's called 2+ times or solves a genuinely complex problem.
**Evidence:** OPINION (practitioner observation)
**Source:** https://medium.com/according-to-context/llms-have-revived-these-5-anti-patterns-in-software-engineering-e685159fc4d8
---
### 11. Duplicate Code (No Consolidation)
**Tell:** Identical or nearly identical code blocks solving the same problem in multiple locations; failure to consolidate into reusable functions.
**Concrete example:**
```python
# In method A
total = sum([x for x in data if x > 0])
# In method B (same logic, not extracted)
total = sum([x for x in data if x > 0])
```
**Fix:** Extract to a helper function. `total = sum_positive(data)`. If you notice identical logic in two places, refactor immediately.
**Evidence:** OPINION (practitioner observation)
**Source:** https://medium.com/according-to-context/llms-have-revived-these-5-anti-patterns-in-software-engineering-e685159fc4d8
---
### 12. Insufficient Test Coverage
**Tell:** Generated code ships with no unit tests. Test cases only added when explicitly prompted.
**Fix:** Write tests from the start. At minimum: one test for the happy path, one for an edge case or error condition. Many AI models default to skipping tests; intentionally include them.
**Evidence:** OPINION (practitioner pattern from code review)
**Source:** https://medium.com/according-to-context/llms-have-revived-these-5-anti-patterns-in-software-engineering-e685159fc4d8
---
### 13. Generic Variable Names
**Tell:** Overly generic names (data, temp, result, temp_var_1) or random sequences when context is unclear.
**Concrete example:**
`temp_var_1`, `x`, `data_holder_42` vs. meaningful names reflecting domain: `userInputBuffer`, `responsePayload`.
**Fix:** Name every variable after what it holds. `temp` is never acceptable. `user_id`, `parsed_response`, `error_code` are better. When you're tempted to use `data`, ask yourself: "data of what?"
**Evidence:** OPINION (practitioner observation)
**Source:** https://www.clrn.org/how-can-you-tell-if-code-is-ai-generated/
---
### 14. Invented Abstractions (Unnecessary Layers)
**Tell:** Extra layers of indirection, wrapper functions, or classes that don't solve the immediate problem; rigid abstractions that don't fit the specific use case.
**Concrete example:**
```python
class DataProcessor:
def process(self, data):
return self._transform(data)
def _transform(self, data):
return self._filter(data)
def _filter(self, data):
return [x for x in data if x > 0]
```
Simpler: `[x for x in data if x > 0]`
**Fix:** Use the simplest structure that solves the problem. If a one-liner works, use it. If you need a function, write a function. Don't add a class wrapper unless it genuinely organizes state or behavior.
**Evidence:** OPINION (practitioner observation)
**Source:** https://medium.com/according-to-context/llms-have-revived-these-5-anti-patterns-in-software-engineering-e685159fc4d8
---
### 15. Variable Error Handling (Model-Dependent)
**Tell:** Error handling varies wildly by AI model and context. GPT-4o-Mini: 3.3% defensive checks. Gemini 2.5 Flash: 21.3%. Claude 3.5 Haiku: 23.3%.
**Fix:** Include error handling deliberately and proportionally. For critical functions (network calls, file I/O, parsing), add try-catch or input validation. For simple logic, skip unnecessary checks. Consistency within *your* codebase matters more than matching a reference model.
**Evidence:** EMPIRICAL (measured defensive coding practice frequency per model)
**Source:** https://www.augmentcode.com/guides/debugging-ai-generated-code-8-failure-patterns-and-fixes
---
### 16. LPcodedec Detection (Stylometric Signature)
**Tell:** LLM-paraphrased code can be detected via stylometric analysis even when logic is unchanged, achieving 87-93% F1 score.
**Fix:** This is automatically addressed by writing naturally (varying function length, naming, indentation, comments). If you're rewriting someone else's code, add your own style (variable names, function size, comment density).
**Evidence:** EMPIRICAL (F1 score and performance benchmark from LPcodedec detection study)
**Source:** https://arxiv.org/html/2502.17749v2

# De-Aification: AI Detection Tools and Methodology
Understanding how AI-detection tools work helps you understand what markers are actually detectable.

## Overview
Most AI-detection tools use one of three approaches:
1. **Perplexity/burstiness metrics** (fast, unreliable for mixed text)
2. **Stylometric features** (linguistic fingerprinting, more reliable)
3. **Transformer-based classifiers** (neural networks trained on AI vs. human text)
No single detector is perfect. False positive rates vary, and effectiveness degrades when text is edited or paraphrased.

## Detection Methodology: How Detectors Work
### Stylometric Feature Analysis (Most Reliable)
Detectors analyze these linguistic markers:
**Lexical Diversity Features (6):**
- Type-Token Ratio (unique words / total words)
- Hapax legomena rate (words appearing once)
- Word count, character count per word
**Syntactic Complexity (12):**
- Average sentence length, sentence length variance
- Punctuation frequency
- Complex verbs, adjectives, contractions
**Sentiment (4):**
- Polarity (positive/negative)
- Subjectivity
- Emotional word frequency
**Readability (2):**
- Flesch Reading Ease
- Gunning Fog Index
**Named Entities (4):**
- First-person pronouns (I, me, we)
- Direct address (you, your)
- Person/date/entity mentions
**Uniqueness (3):**
- Bigram uniqueness (2-word sequences)
- Trigram uniqueness (3-word sequences)
- Syntax variety
**Example:** A detector scores your text on all 31 features, then a classifier determines likelihood of AI origin based on the feature profile.
**Evidence:** EMPIRICAL (StyloAI methodology, published feature extraction framework)
**Source:** https://arxiv.org/html/2405.10129v1
---
### Token-Level Surprisal Analysis (DivEye)
**Approach:** Measure how "surprised" a language model is by each word. AI text shows low surprisal variance (predictable); human text shows high variance (more surprising word choices).
**Features:**
- Mean surprisal (average predictability)
- Variance of surprisal (fluctuation in predictability)
- Skewness and kurtosis (shape of surprisal distribution)
- First and second-order dynamics (changes in surprisal over time)
**Effectiveness:** Captures the "rhythm" of text. Human writing has unexpected word choices; AI text flows along the most predictable path.
**Evidence:** EMPIRICAL (DivEye detector design, arxiv publication)
**Source:** https://arxiv.org/html/2509.18880v1

## Detector Limitations and Failure Modes
### Perplexity and Burstiness Alone (Unreliable)
**Problem:** Perplexity fails on text that appears in training data (Declaration of Independence, Wikipedia articles) because the model optimized on those texts, making them indistinguishable from AI.
**Problem:** Burstiness unfairly penalizes non-native English speakers, who naturally produce lower burstiness and get flagged as AI.
**Solution:** Detectors now combine perplexity with other methods (stylometric features, transformer classifiers). Use perplexity as one signal, not the only signal.
**Evidence:** EMPIRICAL (documented failure cases)
**Source:** https://www.pangram.com/blog/why-perplexity-and-burstiness-fail-to-detect-ai
---
### False Positive Conditions
**Short text (< 100 words):** Reduces accuracy significantly. Detectors need sufficient sample size to extract reliable stylometric features.
**Formulaic content:** 5-paragraph essays, heavily structured articles, scientific abstracts (with statistics and technical language) trigger false positives. These resemble AI patterns (uniform structure, formal language) even when human-written.
**Edited/polished text:** Light grammar editing (using Grammarly or similar) increases false positive likelihood. The editing creates patterns similar to AI smoothing.
**Evidence:** EMPIRICAL (documented conditions from Originality AI and other vendors)
**Source:** https://originality.ai/blog/ai-content-detector-false-positives
---
### Human Accuracy Baseline
**Human detection accuracy without tools: 55%.** Essentially a coin flip. Humans cannot reliably detect AI text by reading alone.
This establishes why tools are needed, but also why tools must be used carefully. Tools are not perfect either, but they're better than human guessing.
**Evidence:** EMPIRICAL (University of Washington study)
**Source:** https://originality.ai/blog/can-humans-detect-chatgpt

## Myth: Distinctive ChatGPT Words
**Claim:** ChatGPT overuses words like "delve," "embark," "tapestry."
**Reality:** Analysis of 10M+ words of ChatGPT output shows top words are generic: "which, such, more, create, their, example." Same as human text. "Delve" appears 146 times (not the thousands implied by viral claims).
**Lesson:** AI models don't have forbidden words; they have stylistic fingerprints (perplexity, burstiness, lexical diversity). Generic superlatives are a sign of marketing copy, not AI specifically.
**Evidence:** EMPIRICAL (corpus analysis contradicting viral myths)

## When Not to Trust Detectors
1. **Heavily edited text:** If you've rewritten, paraphrased, or hand-edited AI output, detectors struggle.
2. **Short text:** Under 100 words, accuracy drops significantly.
3. **Formulaic human text:** Professional writing, academic papers, technical documentation may resemble AI patterns even when human-written.
4. **Mixed content:** AI-edited human text or human-edited AI text confuses detectors.
5. **Non-English or ESL:** Detectors trained on English may over-flag non-native English writers.
---
## Detector As One Signal, Not The Signal
**Good practice:** Use a detector as one input, not the final arbiter. If a detector flags text as 70% AI, investigate manually:
- Is the structure formulaic?
- Are there specific details and examples?
- Is the voice consistent and distinctive?
- Do the citations check out?
**Manual inspection + detector confidence = stronger conclusion than detector alone.**
---
## Tools Mentioned (By Availability)
- **GPTZero** (gptzero.me): Widely available, web-based, free tier
- **Originality AI** (originality.ai): Subscription, good accuracy on long-form
- **Copyleaks** (copyleaks.com): Enterprise option, API available
- **Pangram** (transformer-based, limited availability): Referenced in research, not widely available as product
- **Local stylometric analysis**: Can write simple Python scripts to compute TTR, burstiness, hapax rate
---
## Conclusion
AI detection is improving but not perfect. The best approach to de-aification is:
1. Know the tells (perplexity, burstiness, lexical diversity, structural patterns)
2. Read manually for voice, specificity, and authenticity
3. Use a detector as a checkpoint, not a verdict
4. Focus on writing naturally, not on "fooling" detectors
The rules in the other reference files (writing, coding, visual, marketing) are the detectable tells. Follow them, and your work will be distinguishable from AI output.

## Primary Marketing Tells (Apply Core Writing Rules)
### 1. Absence of Voice / Brand Personality
**Tell:** Generic, corporate tone that could apply to any brand. No distinctive word choices, no personality markers, no humor, no quirks.
**Fix:** Inject brand voice everywhere. If your brand is playful, use casual language and jokes. If serious, use domain-specific terminology and authority. Add personal observations and opinions. Every sentence should sound like your brand, not a template.
**Evidence:** OPINION (marketing practice)
---
### 2. Excessive Formal Language
**Tell:** Overuse of formal discourse markers (moreover, furthermore, consequently) in social media posts and ad copy where casual language is expected.
**Concrete example:**
"Furthermore, our product solves this problem. Moreover, it is cost-effective."
(Wrong for Twitter/Instagram; right for a white paper)
**Fix:** Match formality to platform. Twitter/TikTok: casual, punchy, short. LinkedIn: professional but not stiff. Website copy: varies by section. Remove formal connectors in social media entirely.
**Evidence:** OPINION (marketing platform conventions)
---
### 3. Lack of Specificity / Vagueness
**Tell:** General claims without numbers, examples, customer names, or timestamps.
**Concrete example:**
"Many customers report improvements" vs. "Netflix saved 40% on encoding costs after switching to H.265"
**Fix:** Always include specific numbers, customer names (with permission), dates, and measurable outcomes. Case studies should include before/after metrics. Testimonials should include role and company.
**Evidence:** OPINION (marketing effectiveness)
---
### 4. Overuse of Superlatives
**Tell:** Every claim is maximal: "best," "leading," "revolutionary," "game-changing," "industry-first."
**Fix:** Use superlatives sparingly, only for genuinely differentiated claims. For other features, use measured language: "faster," "more efficient," "simpler." Let data speak instead of hype.
**Evidence:** OPINION (marketing credibility)

### 5. Call-to-Action Repetition
**Tell:** CTA appears word-for-word multiple times in the same piece. "Sign up today" repeated in headline, subheadline, and button.
**Fix:** Vary CTAs. "Get started," "Start free trial," "Schedule a demo," "See pricing" — use different phrasings. CTA variation feels intentional and less formulaic.
**Evidence:** OPINION (copywriting best practice)

**Tell:** Body text that fails WCAG AA accessibility standards in dark themes. Contrast ratio < 4.5:1 fails AA standard.

### 2. Colored Left-Border Cards
**Tell:** Colored left border on card containers (often 4-6px left border in vibrant accent color). Described as "almost as reliable a sign of AI-generated design as em-dashes for text."

Feature card with bright teal/purple/pink left border, grey background, white text.

# De-Aification: Writing Tells

## Linguistic Metrics (Measurable Tells)
### 1. Low Perplexity (Predictable Vocabulary)
**Tell:** Uniform word predictability throughout. Text flows along the path the language model expected, with no surprising vocabulary or structural choices.
**Fix:** Insert unexpected word choices within natural context. Use domain-specific jargon, uncommon verbs, concrete nouns that feel justified by the topic. Add phrases that could only come from observation.
**Evidence:** EMPIRICAL | **Source:** https://www.tryleap.ai/learn/perplexity-vs-burstiness
---
### 2. Low Burstiness (Uniform Sentence Length)
**Tell:** Consistent sentence length throughout; no rhythmic variation between short punchy statements and longer flowing ones.
**Fix:** Deliberately alternate sentence length. Write one short sentence. Then a longer, complex one. Then another short one. Vary within each paragraph.
**Evidence:** EMPIRICAL | **Source:** https://www.tryleap.ai/learn/perplexity-vs-burstiness
---
### 3. Low Lexical Diversity (Repetitive Vocabulary)
**Tell:** Type-Token Ratio (unique words / total words) clusters around 0.45-0.55. Human writing averages 0.60+; a 500-word AI passage uses 225 unique words while humans use 300+.
**Fix:** Replace repeated words with synonyms or restructure to use different vocabulary. Expand your word palette deliberately. If you've used "significant" twice, use "substantial," "notable," "considerable" the next times.
**Evidence:** EMPIRICAL | **Source:** https://arxiv.org/html/2509.18880v1
---
### 4. Low Hapax Legomenon Rate (Few One-Off Words)
**Tell:** Fewer words appearing only once compared to human text. Humans use more single-occurrence words (unique observations, specific details). AI reuses vocabulary more evenly.
**Concrete example:**
Human: "The dilapidated storefront, once teeming with commerce, now stood as a monument to obsolescence." (dilapidated, teeming, obsolescence each appear once)
AI: Reuses common words repeatedly
**Fix:** Use specific, unusual words when appropriate; don't fear one-off vocabulary. If a word describes something perfectly once, use it once and move on. Embrace specificity over repetition.
**Evidence:** EMPIRICAL | **Source:** https://arxiv.org/pdf/2606.04177
---
### 5. Distinctive POS Bigram Patterns
**Tell:** Function word sequences (DETERMINER-NOUN, ADJECTIVE-NOUN) appear with non-random, machine-predictable frequency. Statistical signature betrays LLM origin.
**Fix:** This is difficult to fix manually. Instead: read work aloud and listen for naturalness. Rephrase sentences that sound formulaic. Break up patterns by moving words or restructuring clauses.
**Evidence:** EMPIRICAL | **Source:** https://arxiv.org/pdf/2606.04177
---
### 6. High N-gram Repetition
**Tell:** Multi-word sequences (3+ words) repeating 3+ times across sections. Phrases like "As mentioned earlier," "It is important to note," "In conclusion" appear multiple times. AI shows high n-gram repetition; humans vary phrasing.
**Fix:** Delete repetitive multi-word phrases. Create a list of phrases you've used > once; replace alternates with different constructions. "As mentioned earlier" → "Earlier, I noted..." → "Recall that..." etc.
**Evidence:** EMPIRICAL | **Source:** https://searchatlas.com/blog/ai-patterns-in-writing/

## Stylistic Patterns (Opinion-Based but Consistent)
### 7. Formal Discourse Markers (Overuse)
**Tell:** Frequency of formal connectors (furthermore, moreover, consequently, additionally) exceeds 20% of sentences, appearing at paragraph boundaries with formulaic consistency.
**Concrete example:**
"Furthermore, this approach has merit. Moreover, the evidence supports this. Additionally, research confirms this. Consequently, we proceed forward."
**Fix:** Delete 50% of formal connectors. Replace with natural transitions: short sentences connecting ideas, or no connector at all. Use connectors only when genuinely needed.
**Evidence:** OPINION | **Source:** https://searchatlas.com/blog/ai-patterns-in-writing/
---
### 8. Excessive Hedging Language
**Tell:** Elevated frequency of uncertainty markers (may, might, could, seem, suggest, appear) softening claims throughout unrelated sections, creating confidence-eroding phrasing.
**Concrete example:**
"This may possibly indicate that research suggests we could consider that it might appear that..."
**Fix:** Delete hedging language except where genuine uncertainty exists. "This indicates" instead of "This may suggest." Assert. If you're unsure, restructure: "We don't yet know whether..." rather than "It might seem that..."
**Evidence:** OPINION | **Source:** https://searchatlas.com/blog/ai-patterns-in-writing/

### 9. Structural Predictability (Symmetrical Sections)
**Tell:** Symmetrical paragraph lengths, formulaic organization. Sections mirror each other; conclusions restate introductions with predictable structure. Five 4-paragraph sections each concluding with "In summary, X is important."
**Fix:** Vary section length deliberately. Some sections 1 paragraph, others 5. Vary conclusion style. Kill the formula.
**Evidence:** OPINION | **Source:** https://searchatlas.com/blog/ai-patterns-in-writing/
---
### 10. Uniform Paragraph Structure (Predictable SVO)
**Tell:** Every sentence follows subject-verb-object construction across consecutive sentences; no abrupt structural shifts.
**Concrete example:**
"The study examined X. Researchers found Y. This indicates Z. Evidence shows A."
**Fix:** Vary sentence structure. Invert: "Found by researchers: Y." Use fragments: "Evidence? A." Lead with object or modifier: "Throughout this analysis, X emerges as central."
**Evidence:** OPINION | **Source:** https://searchatlas.com/blog/ai-patterns-in-writing/
---
### 11. Absence of Specific Detail
**Tell:** Generalized statements lacking timestamps, named sources, personal observation, sensory description, or firsthand reference. "Studies show benefits" without researchers, dates, citations. No "I noticed," "On March 3rd," "The smell of..."
**Fix:** Add verifiable specifics everywhere. Name researchers, include dates and URLs, cite DOIs. Include personal observation: "When I tested this in April, the response time dropped 40%." Use sensory language: colors, textures, sounds, smells when relevant.
**Evidence:** OPINION | **Source:** https://searchatlas.com/blog/ai-patterns-in-writing/
---
### 12. Fabricated or Vague Sourcing
**Tell:** References formatted correctly but lacking verifiable existence when checked (titles, authors, DOIs, URLs). "Smith et al. (2023) in their landmark study..." — format looks academic but the authors and publication don't exist.
**Fix:** Every citation must be verifiable. If you cite something, confirm it exists before submitting. Use only real sources. If you're unsure, rewrite without the citation.
**Evidence:** OPINION | **Source:** https://searchatlas.com/blog/ai-patterns-in-writing/
---
### 13. Token Surprisal Variance (High Predictability)
**Tell:** Low variance and entropy in token-level surprisal. Human text exhibits significantly higher variance and extreme fluctuations; AI text is smooth and predictable.
**Fix:** Read aloud. Where you hear smoothness, introduce a rougher word or structure. Create moments of surprise: unusual word choices, short sentences interrupting longer ones, tonal shifts.
**Evidence:** EMPIRICAL | **Source:** https://arxiv.org/html/2509.18880v1
